# ADR 002 Isolar a regra do Ranking com Ports and Adapters

Data: 26 de outubro de 2026. Estado: implementado e validado localmente para a entrega dos Desafios 1 e 2.

## Contexto e RFs

O RF01 consulta Ranking; o contexto do RF02 prevê evolução das regras de gamificação. No Desafio 1, o monólito foi agrupado por capacidade e Ranking passou a consultar a API pública de Usuário. Ainda assim, `RankingService` conhecia diretamente esse fornecedor, e a expressão de pontuação existia na aplicação e no ORDER BY da consulta JPA.

O laboratório trata somente o Ranking. Não implementa badges nem reescreve os fluxos de matrícula e assinatura.

## RNFs selecionados como ASRs

- D2 A1 Manutenibilidade: centralizar a regra em domínio sem framework evita espalhar a fórmula entre aplicação e consulta de banco.
- D2 A2 Testabilidade: uma porta de saída permite executar a regra e o caso de uso com fonte em memória e verificar o adapter relacional separadamente.
- D2 A3 Modificabilidade: separar aquisição de dados e cálculo permite trocar a fonte sem alterar domínio, caso de uso ou contrato HTTP.

Todos pertencem a Supportability em FURPS+. Facilidade de evolução foi analisada como consequência desses atributos, sem criar um quarto ASR.

## RPCs

Core continua Spring Boot; reaproveitar regras existentes; não reescrever o produto inteiro para aplicar um padrão. A fórmula já existente é `100 * cursos concluídos + moedas`, com Ranking descendente. Mantemos Java 17, banco relacional e endpoint `/api/ranking` da base fornecida. A equipe real possui quatro integrantes; a premissa didática de seis desenvolvedores pertence ao cenário do Desafio 1.

## Alternativas e trade offs

| Alternativa | Benefício | Custo ou limite |
| --- | --- | --- |
| Manter aplicação dependente da API de Usuário e ordenação no SQL | Menor quantidade de classes e ordenação no banco | Regra duplicada; fornecedor de dados definido na aplicação; regra menos isolada |
| Ports and Adapters na fatia Ranking | Regra Java pura, contrato definido pelo consumidor, adapters substituíveis | Novos tipos e mapeamentos; ordenação passa a ocorrer em memória |
| Reestruturar todo o Core com Clean ou Onion | Poderia padronizar dependências do produto inteiro | Mudança extensa sem evidência proporcional; contraria evolução incremental da RPC |

## Decisão

Aplicar Ports and Adapters apenas à leitura do Ranking. `ParticipanteRanking` calcula os pontos; `Ranking` ordena os participantes. Ambos dependem apenas de Java e do próprio domínio.

`CarregarParticipantes` é uma porta de saída definida pelo caso de uso. `RankingService` recebe essa interface por construtor. Em execução, Spring injeta `JpaParticipantesAdapter`, que usa a API pública `ConsultaPontuacao` de Usuário; a consulta JPA e suas entidades continuam internas ao módulo de Usuário. Nos testes, `ParticipantesEmMemoria` implementa a mesma porta.

A consulta deixou de calcular e ordenar a pontuação no SQL. O caso de uso aplica a mesma regra de domínio a qualquer fonte. O HTTP conserva os campos e valores já esperados.

## Relação com DDD Clean e Onion

DDD trata modelagem e linguagem do domínio; Hexagonal trata portas e adapters; Clean e Onion tratam dependências voltadas para o centro. Podem se combinar. Neste laboratório usamos uma fatia de Ports and Adapters e dados de domínio imutáveis, sem afirmar que implementamos DDD completo ou todas as camadas de Clean/Onion. A aplicação ainda mapeia o DTO existente para limitar a mudança.

## Consequências e limites

O domínio não conhece Spring, JPA, HTTP, Mockito ou banco. A mesma suíte de domínio é mantida ao trocar o adapter. A consulta de dados tem uma implementação JPA real testada com H2; não se afirma que um mock validou o banco.

Ordenar em memória custa O(n log n) e a leitura continua sem paginação. Essa escolha favorece o isolamento da regra neste mini lab; não é prova de escalabilidade para 100 mil usuários. Para uma consulta paginada em produção, reavaliar projeção/materialização, índices e ordenação no banco com testes de equivalência da regra. Empates continuam sem critério de desempate de negócio; não há garantia de ordem entre participantes empatados no banco.

Permanecem as dependências diretas de Matrícula e as entidades JPA de Usuário/Curso. O B1 não foi inteiramente convertido para Hexagonal. A contabilização repetida da conclusão de matrícula continua como risco identificado para o trabalho de eventos/idempotência.
